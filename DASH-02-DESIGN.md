# DASH-02 design note: Rollout review

Status: v2, approved in principle 9 Nov 2026, amended to match the live Frames page word for word. Build may start from this version.

## 1. What it is

The second dashboard on the Dashboards page of mjazzly.github.io. It is the data side of two frames on the Frames page:

- **FRAME-04, How to tell a rollout is working**: four stages, one question each (Foundation, Execution, Refinement, Scale), every measure read from a named source. The frame's own rule applies to this dashboard: a measure that cannot be read from a source does not go on the page.
- **FRAME-01, The adoption flight**: three stages, nine checkpoints, and the "Counting who is where" rule: the check-in gives the fast picture, the sources give the true one, and where they disagree the gap is itself a finding. Counted again a month later, the people who moved up a checkpoint are the rollout measure.

Working name: **Rollout review** (sits beside DASH-01, Branch review).

Reader: the **enablement lead** of an AI adoption programme, who decides each week where enablement effort goes. The front page is written for the **programme sponsor**, who asks one question: is the rollout working.

Rules carried from DASH-01 and the site:
- Synthetic data only, generated by a seeded script in a public repo
- Organisation neutral: generic team names, "the assistant platform", no firm, platform, tool or product names, no currency
- Every number on the page traceable to a row in the repo and matched in a recorded check
- A guided read on the site page, visual first, record folded behind a button
- Claude drafts (generator, measures, layout), you review and approve

## 2. Decisions

| Question | Decision | Reason |
|---|---|---|
| Primary reader | Enablement lead, with a sponsor front page | Matches the seat (libraries, exemplars, office hours, pattern tracking). Cost and governance belong to IT and Finance and stay off |
| Pages | One page per FRAME-04 stage question, plus one page for FRAME-01's count | The dashboard then answers the frame's four questions in the frame's own order |
| Outcome | FRAME-04's Scale stage is the outcome page, read from the sources the frame names | A timed workflow study was in v1; it is not a source either frame names, so it is out. Scale already asks "where has it changed the work" |
| Period | 24 weeks, weekly usage, monthly check-in (six check-ins) | Movement between checkpoints needs at least two check-ins; six show a trend |
| Front page unit | FRAME-01's three stages on the front page, nine checkpoints on the drill-down | Nine bars is too much for a sponsor; the enablement lead needs the nine because each carries its own lever |
| Checkpoint placement | Two placements per person per month: **check-in** (self-placed, from the check-in's sixth question) and **source** (derived from the usage, library and question log by stated rules). Both shown, never blended | This is the "Counting who is where" rule made visible, and the strongest difference from any vendor persona chart |
| Cost per use | Tokens per run from the run log, with a cost index against the smaller model (smaller model = 1.0) | FRAME-04 names cost per use as a Refinement measure; tokens keep it checkable with no currency on a public page |
| Repo | New public repo `rollout-review` under mjazzly, read only like the others, added to the Claude GitHub App | Generator, tables, dictionary, check and measures in one place; cross-linked from Dashboards and from Frames |
| Organisation size | 1,200 people, six teams (Consulting, Finance, Operations, Legal, People, Technology), three regions | Large enough for team splits to mean something, small enough to read |
| Fluency or maturity score | None | A composite with no formula is the first thing a senior reader distrusts |

## 3. The sources (tables)

Five source tables, four from FRAME-04's source cards and the check-in from FRAME-01, plus the dimensions that join them. Each lists the live system that would supply it, so swapping the backend later means replacing a CSV with an export of the same columns.

### Facts

| Table | Frame source card | Grain | Columns | Live source |
|---|---|---|---|---|
| fact_question | The question log: one row per question asked, who asked, what the request really was, how hard it was, what was done | question | question_id, question_date, person_id, team, category, difficulty (1 to 3), action_taken (answered, pointed to library, new prompt written, escalated), linked_item_id (nullable), answered_by_person_id (nullable), repeat_flag | Office hours or help channel log |
| fact_usage_week | The usage dashboards: the figures the tools themselves report | person, week | person_id, week_start, days_active, sessions, runs_total, runs_via_library | Platform admin export |
| fact_library_run | The library's records (use side) | item, team, week | item_id, team, week_start, runs, distinct_users | Library run log |
| fact_library_run_person | The library's records (use side, per person); fact_library_run is its roll-up | item, person, week | item_id, person_id, week_start, runs | Library run log |
| fact_test_run | The run log: what each test run cost and what it matched | test run | run_id, item_id, version, run_date, model_tier (standard, smaller), cases_total, cases_matched, tokens_in, tokens_out | Test harness output |
| fact_checkin | The check-in (FRAME-01) | person, month | person_id, checkin_month, q1_access, q2_last_use, q3_trigger, q4_used_on, q5_if_gone, checkpoint_id (q6) | Check-in form |

## 4. dim_checkpoint, from FRAME-01

| id | Stage | Checkpoint | How you tell | The lever |
|---|---|---|---|---|
| 1 | On the ground | No ticket | Has no AI they are allowed to use for work yet | Access, and a reason to use AI in the first week |
| 2 | On the ground | Ticket held | Is allowed to use AI for work, but has not tried it yet | A first task done side by side with someone who already uses AI |
| 3 | On the ground | Checked in | Tried AI once or twice, then stopped | A second task that fits their actual week |
| 4 | At the gate | Through security | Is still working out what AI is allowed for, or has just read the rules | A worked example from their own role |
| 5 | At the gate | Waiting to board | Uses AI only in the weeks a reminder goes out | One recurring task tied to a day of the week |
| 6 | At the gate | Boarding | Has used AI once on real work that went to someone else | Make that recurring task part of their routine |
| 7 | In the air | Takeoff | Uses AI every week on one task, for a month or more | A second task, and a place to share what works |
| 8 | In the air | Above the clouds | Uses AI on several tasks and shares what works | Ask them to show their team |
| 9 | In the air | Frequent flyer | AI is part of how they work every week, and colleagues come to them with questions | Give them a prompt to look after in the library, and point new starters their way |

Stage subtitles from the page: On the ground, Not flying yet; At the gate, Ticket in hand; In the air, Using it every week.

## 5. Source placement rules (v2, tuned once the tables existed)

FRAME-01 says which source separates which checkpoints: the usage dashboards show access and separate Ticket held, Checked in, Waiting to board and Takeoff; the library's records show Boarding, Above the clouds and Frequent flyer; the question log shows Through security. The rules below follow that split. Evaluated per person at each check-in month, over the trailing eight weeks unless stated; the first rule that matches from the top wins.

| Checkpoint | Rule |
|---|---|
| Frequent flyer | Owns a library item, and is answered_by on 3 or more questions in the trailing eight weeks |
| Above the clouds | Active (2 or more days) in 6 of 8 weeks, runs across 2 or more library items, and owns a library item |
| Takeoff | Active in 4 or more consecutive weeks |
| Boarding | At least one library run ever, and fewer than 4 consecutive active weeks |
| Through security | A question in the Rules and allowed use category in the trailing 30 days, and fewer than 2 active weeks in that time |
| Waiting to board | Active in at least one of the trailing eight weeks, and fewer than 4 of them consecutive |
| Checked in | Ever active, none in the trailing eight |
| Ticket held | Seat assigned, never active |
| No ticket | No seat assigned |

v2 changes Takeoff, Waiting to board and Checked in so that the rules place everyone; under v1, 12 to 15 percent of people matched no rule. Checked in is wider than the page wording (it also covers people who used AI for several weeks, then stopped), since FRAME-01 has no separate lapsed checkpoint. Exact wording is in `measures.md`.

The **gap** is check-in checkpoint minus source checkpoint, shown per team as counts of people placing themselves higher, level, or lower than the sources do.

## 6. Pages

Six pages, at most four visuals each. Every page states the frame question it answers, the source tables it reads and the period.

### Page 0: Rollout review (front, sponsor)
- Header line: period, headcount, seats assigned, seats active this week
- **Four stage tiles**, Foundation, Execution, Refinement, Scale, each carrying its FRAME-04 question, one headline measure, a 24-week sparkline, a verdict rule printed under it, and a trend. Verdict "Working" means the threshold is met and "Not yet working" means it is not, with no trend condition. Trend is a separate field: up, flat or down against two months earlier (flat within 1 point), or "No comparison yet" when there is no figure two months earlier. Thresholds are illustrative programme targets that a real programme sets for itself; they are held in `measures.md` and printed on each tile:
  - Foundation: requests matched to a tested prompt that already exists (share of questions with action_taken = pointed to library); threshold 40%
  - Execution: repeat use within 30 days (share of first-time users active again within 30 days); threshold 60%
  - Refinement: tested prompts that pass on the smaller model (share of active items whose latest smaller-tier run passed); threshold 50%
  - Scale: share of people In the air by source placement, latest month against each team's baseline month; threshold 10 points above baseline
- **Stage split**: On the ground, At the gate, In the air as one stacked bar, source placement, latest month against the baseline (each team at its own baseline month)
- **Moved up since last count**: one number, the rollout measure in FRAME-01's words, with seat arrivals shown as a separate number beside it, never folded in

### Page 1: Where people sit (FRAME-01)
- Nine checkpoints as a bar per team, one scale, with a toggle between check-in placement and source placement
- **The gap** per team: higher, level, lower
- **Movement** between the two latest counts: up, held, down, per team, with seat arrivals shown apart
- Largest group per team shown with its lever from dim_checkpoint

### Page 2: Foundation. Which uses matter most, and where do people get stuck?
Read from the question log, the usage dashboards and the library's records.
- Uses logged and ranked by how often they come up (questions by category, ranked)
- Prompts tested against an answer key written first (share of library items with answer_key_first true)
- Requests matched to a tested prompt that already exists (share of questions with action_taken = pointed to library)
- A usage baseline by team: where usage stood at the start (weekly active share over each team's first four weeks after its seats arrive)

### Page 3: Execution. Does it hold up in everyday use?
Read from the usage dashboards, the question log and the run log.
- First use within two weeks of a training session where it was shown (share of attendees with a run on the shown item within 14 days)
- Repeat use within 30 days (share of first-time users active again within 30 days)
- Recurring questions covered by a tested prompt (share of repeat-flagged questions whose category has an active library item)
- Tested prompts passing their cases (share of items whose latest standard-tier run matched all cases)

### Page 4: Refinement. What earns its place, and at what cost?
Read from the run log and the library's records.
- Tested prompts that pass on a smaller model (items whose latest smaller-tier run matched all cases)
- Cost per use (median tokens per run by item, standard against smaller, and the cost index)
- Prompts retired or merged (count by month, with merged_into shown)

### Page 5: Scale. Where has it changed the work?
Read from the question log and the usage dashboards, with the check-in supplying people's own words.
- Impact in people's own words, by team (check-in q5_if_gone, answer options counted per team)
- Uses taken up beyond the first team (library items with runs from 2 or more teams, and the week the second team started)
- Share of people in the air against the baseline (source placement In the air, latest month against the team's baseline month, per team)

One wording note for you: FRAME-04's Scale source line names the question log and the usage dashboards. "People's own words" in this build come from the check-in's fifth question, which is the plainest place to collect them. Either the Scale source line on Frames gains "the check-in", or the question log gains an impact column. I recommend the first; your call, and it does not block the build.

## 7. Planted storylines

Synthetic data with nothing in it gives pages with nothing to say. The generator plants five storylines and the README names them as planted:

1. **Legal**: seats assigned early, most people held at Ticket held across all six counts (the first shape in FRAME-01: the problem is access and the first week)
2. **Finance**: the check-in places many at Takeoff, the sources place them at Waiting to board (the gap as a finding; the second shape: the problem is habit)
3. **Operations**: repeat questions in one category fall sharply after a library item for that category is published in week 12; movement up at the next count
4. **Technology**: two items pass on the smaller model at half the tokens; one item is retired and one merged in month 5 (the Refinement page has something to say)
5. **Consulting**: broad, steady adoption, the highest library share, and the first item taken up by a second team (the benchmark team, and the Scale page's example)

People sits in between with no planted story.

## 8. Measures

Every measure has one definition, written once in `measures.md` and mirrored word for word in the DAX measure description, so the page, the check and the repo agree. The page measures are listed in section 6; the supporting measures:

| Measure | Definition |
|---|---|
| Assigned seats | People whose seat_assigned_week is on or before the week |
| Weekly active share | People with days_active of 2 or more in the week, over assigned seats |
| Library share | runs_via_library over runs_total |
| Repeat flag | A question from the same person in the same category within 30 days of an earlier question by that person |
| Passing | A test run where cases_matched equals cases_total |
| Cost index | Median tokens per run on the standard tier over median tokens per run on the smaller tier, per item |
| Baseline month | For each team, the first check-in month whose trailing eight weeks start on or after the week the team's seats arrive (month 1 cannot be a baseline: no team has had seats for eight weeks, and Takeoff needs four consecutive active weeks) |
| Moved up | People who held a seat at both counts and whose source checkpoint_id at the latest count is higher than at the previous count |
| Seats arrived | People with no seat at the previous count and a seat at the latest count; shown beside Moved up, never folded in |

## 9. The recorded check

Same pattern as DASH-01. A question set (target 18 questions, three per page) is answered by a check script that reads the CSVs directly (DuckDB over the generated tables), and the answers are matched against the Power BI visuals one by one. The count of matches is stated on the site page beside the dashboard, with the question list and answers openable in the repo.

## 10. Repo layout

```
rollout-review/
  README.md            what it is, the planted storylines, how to rerun
  generate.py          seeded generator, writes data/*.csv
  check.py             answers the question set from the CSVs
  data/                the fourteen CSVs
  DICTIONARY.md        every table and column
  measures.md          every measure and placement rule
  CHECK.md             questions, expected answers, match record
  DASH-02-DESIGN.md    this note
```

## 11. Build order

1. Create the repo, add it to the Claude GitHub App
2. Generator and dictionary (Mac, Claude Code); tables and the source placement counts shown to you before any Power BI work, so the planted storylines read as intended
3. Check script and question set, run once against the tables
4. Power BI on the PC over Remote Desktop, measures drafted from measures.md, page by page in the order above, screenshots back for review
5. Match the check against the visuals, record the count
6. Publish to web, site page entry, cross-links from Dashboards and from Frames
7. Nothing on CV or LinkedIn until you say so

## 12. Kept out, on purpose

- Any currency, ROI or loaded cost
- A blended fluency or maturity score
- Cost tracking of licences, unapproved tools, personal account detection
- Individual names or per-person views (team is the lowest grain shown)
- Self-reported time saved as a headline
- A timed workflow study (not a source either frame names)
- A live check-in form or data pipeline; the generator stands in for all sources
